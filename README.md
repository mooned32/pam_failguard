# pam-failguard

Модуль PAM: **отказ** в приёме пароля на заданное число секунд после
неудачной попытки ввода. Экран не зависает, сообщение обычное.

```
неверный пароль  ->  сразу обычное сообщение об ошибке
                 ->  следующие 10 секунд система НЕ ПРИНИМАЕТ НИКАКОЙ пароль
                 ->  через 10 секунд всё работает как обычно
```

## Отличие от похожих механизмов

| Механизм | Что делает | Почему не подходит |
|---|---|---|
| `pam_faildelay` | ждёт внутри обработки неудачи | экран висит 10 с, сообщение появляется потом; вдобавок `select()` обрывается сигналом, так что 10 с превращаются в 6–9 (измерено) |
| `pam_tally2` | копит счётчик неудач и блокирует учётку | счётчик **накапливается** и переживает перезагрузки; `unlock_time` снимает блокировку после паузы, и защита обходится ожиданием; без `unlock_time` учётку запирает навсегда (измерено) |
| `pam_failguard` (этот) | отказывает ровно на `delay` секунд | счётчик сам устаревает, ничего не переживает перезагрузку, ручная разблокировка не нужна |

## Семантика

* `delay=N` — **секунды** (целое число). Намеренно отличается от `pam_faildelay`,
  где `delay` задаётся в микросекундах.
* `deny=N` — сколько неудачных попыток нужно, чтобы включился отказ.
* `debug` — подробные сообщения.

При `deny=1 delay=10`:

1. Неудачная попытка → счётчик +1, метка времени = сейчас. Сообщение об
   ошибке показывается сразу.
2. Любая попытка в следующие 10 секунд → **отказ** (даже с верным паролем).
   Окно **скользит**: каждая *неудачная* попытка отсчитывает 10 секунд заново,
   поэтому непрерывный перебор держится бесконечно. Отказ по действующему
   окну таймер не продлевает — верный пароль не неудачная попытка.
3. Тишина длиннее 10 секунд → отказ снимается, счётчик обнуляется.
4. Счётчик не влияет на длину отказа: она всегда ровно `delay` и не растёт.

## Стек

```
auth	[success=2 default=ignore]	pam_unix.so nullok_secure
auth	optional	pam_failguard.so record deny=1 delay=10
auth	requisite	pam_deny.so
auth	required	pam_permit.so
auth	required	pam_failguard.so refuse deny=1 delay=10
```

* `record` — после `pam_unix` с `default=ignore`, поэтому выполняется
  **только при неудаче** и записывает метку времени. При успехе пропускается.
* `refuse` — последним модулем, срабатывает **только после успешной** проверки
  пароля: если окно не истекло, вход всё равно отклоняется.
* `success=2` — при успехе `pam_unix` перепрыгивает `record` и `pam_deny`,
  попадая на `pam_permit`; `refuse` остаётся последним и может отказать.

Результат проверки пароля модулю, стоящему **до** `pam_unix`, недоступен —
поэтому «записать неудачу» и «отказать» разнесены по двум позициям.

## Почему отказ обязательно ПОСЛЕ проверки пароля

Это не украшение, а требование greeter'а. В `unity-greeter`
(`src/greeter-list.vala`) есть флаг:

```vala
protected bool prompted = false;            // строка 776
...
    prompted = true;                         // строка 803, внутри диалога PAM
...
if (prompted)
    show_message (_("Invalid password, please try again"), true);   // 859
else
    show_message (_("Failed to authenticate"), true);              // 870
```

`prompted` выставляется **только когда PAM действительно запросил пароль**.
Если стек отказывает до `pam_unix`, диалог не вызывается, `prompted` остаётся
`false`, и окно входа показывает аварийный экран «Failed to authenticate» с
кнопкой Retry вместо обычного сообщения. Это и было причиной появления Retry
при первой реализации — версия с `check` перед `pam_unix`.

Цена решения: пароль реально проверяется, и отказ наступает через ~2 с
(время штатной обработки), а не мгновенно. Плата за правильное поведение окна.

## Сборка

Достаточно штатного компилятора, `libpam0g-dev` **не требуется** — нужные
объявления ABI Linux-PAM находятся в самом исходнике.

```sh
make
# или напрямую:
cc -Wall -O2 -fPIC -shared -o pam_failguard.so src/pam_failguard.c
```

## Установка и откат

```sh
make install     # собрать и положить модуль в каталог модулей PAM
make uninstall   # убрать модуль
```

Правки в `/etc/pam.d/common-auth` вносятся отдельно, вручную — дифф и
объяснение в `PAM-CONFIG.md`. Каталог состояния `/var/lib/pam-failguard`
модуль создаёт сам.

## Окно не продлевается отказом

Отказ по действующему окну **не сдвигает таймер**. Окно всегда отсчитывается
от последней неудачной попытки.

Продление здесь ломало разблокировку экрана. Диалог блокировки
`gnome-screensaver` повторяет проверку каждые 3 секунды и имеет жёсткий предел
`MAX_FAILURES = 5` попыток, после которого окно закрывается вовсе
(`src/gnome-screensaver-dialog.c`, `auth_check_idle`). Пока окно продлевалось,
оно не истекало никогда, пока пользователь продолжал жать Enter, поэтому:

* разблокировать экран было невозможно в принципе;
* после 5 попыток диалог закрывался, и приходилось выходить и входить через
  основное окно входа.

Измерено на обеих версиях, сценарий «неудача, затем верный пароль каждые
3 секунды»:

| Версия | Результат |
|---|---|
| с продлением | 5 отказов подряд, вход невозможен, диалог закрывается |
| без продления | 2 отказа, затем вход |

Это в точности требование «отказывать ровно 10 секунд»: верный пароль,
отклонённый из-за окна, не является неудачной попыткой и не должен сдвигать
таймер. Скользящее окно сохраняется — каждая *неудачная* попытка обновляет
метку времени.

## Отказоустойчивость

* Любая ошибка ввода-вывода → `PAM_IGNORE`, вход **не** блокируется.
  Сломавшийся каталог состояния не должен запирать учётки.
* Часы ушли назад → метка считается просроченной (тоже открыть).
* Аутентификация, при которой пароль не запрашивается вовсе (например, по
  публичному ключу), ложной записи о неудаче не создаёт — модуль не мешает
  таким входам.
* Состояние самоустаревает: ручная разблокировка не нужна.

## Измеренные результаты (Ubuntu 15.10, PAM 1.1.8, i686)

Реальный клиент `su` в псевдотерминале:

| Шаг | Время | Итог |
|---|---|---|
| верный пароль, неудач не было | 0.03 с | вход |
| неверный пароль | 2.20 с | отказ |
| **верный сразу после** | 1.94 с | **отказ** |
| **верный ещё раз** | 2.35 с | **отказ** |
| верный после паузы 11 с | 0.03 с | вход |
| снова неверный | 1.61 с | отказ |
| верный сразу | 2.21 с | отказ |

Пример записи в `/var/log/auth.log` (журнал на английском — системном языке):

```
su[2705]: pam_failguard(su:auth): pam_failguard: authentication refused for user [pamlab], 1 failed logins, 7 s remaining
```

### Границы проверки

Живой ввод в окно входа автоматически не воспроизводится, поэтому greeter
проверен вручную. Таблица выше — измерения реального клиента `su` в
псевдотерминале, то есть проверка настоящего пути входа, а не модуля в
отрыве от системы.

## Файлы

```
src/pam_failguard.c              исходник модуля
Makefile                         сборка
etc/pam.d/common-auth            итоговый конфиг (снимок из системы)
etc/pam.d/common-auth.pristine   исходный конфиг (снимок из системы)
verify/pam-failguard-check.py    проверка исходов и окна
CHANGES.md                       изменения по замечаниям
PAM-CONFIG.md                    все правки конфигурации PAM
```

Переносить на другую систему нужно **исходник**, а не собранный `.so`: модуль
должен быть собран под архитектуру целевой машины.

```sh
sudo -u test python3 verify/pam-failguard-check.py <пользователь> <пароль> 10
```
