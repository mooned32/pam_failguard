| Размер журнала на момент проверки | 734 строки |

## 1. Что это такое

`/var/log/auth.log` — обычный текстовый файл, в который операционная система записывает
все попытки входа в систему и связанные с этим действия: ввод пароля, подключение по
SSH, запуск программ от имени администратора, смену пароля, создание и изменение
учётных записей.

По сути это «книга регистрации» компьютера: кто, когда и как пытался войти и что
делал после входа. Файл нужен администратору для ответов на вопросы «когда войдёт
последний раз?», «были ли попытки входа с чужого адреса?», «кто менял пароль?».

## 2. Как запись попадает в файл

Чтобы запись оказалась в файле, она проходит четыре шага:

1. **Программа сообщает о событии.** Любая программа (`sshd`, `sudo`, `login`,
   модули PAM) вызывает системную функцию `syslog()` и передает текст сообщения,
   уровень важности и тип события (например, «аутентификация»).

2. **Сообщение попадает в общую очередь.** Программа отправляет его в специальный
   файл-сокет `/dev/log`. Этот сокет принадлежит демону `systemd-journald`, который
   сначала сохраняет копию сообщения в собственном журнале (доступном через
   команду `journalctl`).

3. **Сообщение пересылается дальше.** `journald` выкладывает его в соседний сокет
   `/run/systemd/journal/syslog`. Его читает демон `rsyslogd` — основной
   «диспетчер» журналов.

4. **Демон `rsyslog` раскладывает по файлам.** По своим правилам он смотрит на тип
   сообщения и записывает его в нужный файл. Все сообщения типа «аутентификация»
   (`auth`) и «защищённая аутентификация» (`authpriv`) попадают в `/var/log/auth.log`.

Схемой это можно представить так:

```
программа (sshd, sudo, login, PAM)
      │  вызов syslog()
      ▼
   /dev/log ──────────► systemd-journald ──► собственный журнал (journalctl)
                              │
                              ▼
                /run/systemd/journal/syslog
                              │  читает rsyslogd
                              ▼
                        /var/log/auth.log
```

### Правила маршрутизации

Правило, которое формирует наш файл, находится в `/etc/rsyslog.d/50-default.conf`:

```
auth,authpriv.*          /var/log/auth.log
*.*;auth,authpriv.none   -/var/log/syslog
```

Первая строка говорит: «записи типа `auth` и `authpriv` всех уровней важности
сохраняй в `/var/log/auth.log`».

Вторая строка исключает эти же записи из общего файла `/var/log/syslog`, чтобы
одно и то же событие не хранилось в двух местах.

Настройки создания самого файла заданы в `/etc/rsyslog.conf`:

```
$FileOwner   syslog
$FileGroup   adm
$FileCreateMode 0640
$RepeatedMsgReduction on
```

## 3. Формат записи

Каждая запись — одна строка, формата «дата, имя компьютера, программа, сообщение»:

```
Sep 30 15:01:12 ubuntu sshd[3001]: Accepted publickey for root from 192.168.122.1 port 49576 ssh2: ED25519 SHA256:mu+9vfb/gDno+DpoJrMZgLGTqYyCzCvw5DIkta7aDes
```

| Поле | Пример | Что означает |
|---|---|---|
| Месяц | `Sep` | Момент события (сентябрь) |
| Число | `30` | День месяца |
| Время | `15:01:12` | Часы:минуты:секунды, 24-часовой формат, локальное время |
| Имя компьютера | `ubuntu` | Имя машины, где произошло событие |
| Программа | `sshd` | Название программы-источника |
| Номер процесса | `[3001]` | Идентификатор процесса (PID) — позволяет отличить параллельно работающие сеансы |
| Разделитель | `:` | Отделяет шапку от текста |
| Текст сообщения | `Accepted publickey for root...` | Описание самого события |

**Важно:** год в записи не указывается. Год появляется только после ротации, когда
старые записи переименовываются в `auth.log.1`, `auth.log.2.gz` и так далее. При
анализе событий старых лет это надо учитывать.

## 5. Как искать нужные записи

Искать обычной командой `grep`, но с ключом `-a`: в файле есть одна строка с
служебными символами, и без этого ключа `grep` считает файл текстовым без
поддержки поиска и отказывается работать.

```bash
# все неудачные попытки входа
grep -a "authentication failure" /var/log/auth.log

# все подключения по SSH
grep -a "Accepted" /var/log/auth.log

# что происходило с конкретным пользователем
grep -a "user=test" /var/log/auth.log

# входы в определённый день
grep -a "^Sep 30" /var/log/auth.log

# смена пароля, создание пользователя
grep -aE "useradd|usermod|chage|passwd" /var/log/auth.log
```

## 6. Права доступа, объём и хранение

| Параметр | Значение | Смысл |
|---|---|---|
| Владелец | `syslog` | Демон `rsyslog` пишет файл от своего имени |
| Группа | `adm` | Читать могут только администраторы |
| Права | `0640` (`-rw-r-----`) | Обычный пользователь файл прочитать не может |
| Ротация | еженедельно, `rotate 4` | Старые записи хранятся около месяца |
| Сжатие | включено | Старые копии сохраняются в виде `.gz` |
| Место на диске | ограниченное | Записи старше месяца удаляются |

Правила ротации описаны в `/etc/logrotate.d/rsyslog`:

```
/var/log/auth.log
{
    rotate 4
    weekly
    missingok
    notifempty
    compress
    delaycompress
    sharedscripts
    postrotate
        service rsyslog rotate >/dev/null 2>&1 || true
    endscript
}
```

## 7. Особенности и ограничения

1. **Копии в двух местах.** Те же события доступны командой `journalctl`. Журнал
   `journald` на этой системе не сохраняется после перезагрузки (каталог
   `/var/log/journal` отсутствует), поэтому `/var/log/auth.log` — единственный
   долговременный источник записей.

2. **Глубина хранения невелика.** Еженедельная ротация с хранением 4 копий даёт
   около 4 недель. Для анализа инцидентов давности в несколько месяцев данных уже
   не будет.

3. **Отсутствует система аудита.** Утилита `auditd` не установлена, поэтому
   отдельного детального журнала аудита (`/var/log/audit/audit.log`) нет. Фиксируются
   только события, которые записывают программы уровня пользователя.

4. **Журнал можно стереть.** Централизованного копирования записей на другой сервер
   не настроено, удалён файл — удалена и история событий.

5. **Нет года.** Как указано в разделе 3, год в строке не проставляется.
