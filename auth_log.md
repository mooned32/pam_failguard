# Журнал входа в систему: `/var/log/auth.log`

**Для составителей отчётов и документов по эксплуатации.**

| | |
|---|---|
| Система | Ubuntu 15.10, компьютер `ubuntu` |
| Файл журнала | `/var/log/auth.log` |
| Дата проверки | 12.10.2026 |

---

## 1. Что это

Обычный текстовый файл, куда система записывает **все попытки входа** и действия,
связанные с правами: кто, когда и откуда пытался войти, что получилось, что человек
сделал после входа.

Проще говоря — это «книга регистрации» компьютера. Она нужна, чтобы потом ответить
на вопросы:

- когда последний раз заходил этот пользователь?
- были ли попытки входа с чужого адреса?
- кто и когда менял пароли и учётные записи?
- кто запускал команды от имени администратора?

Файл читают только администраторы — см. раздел 6.

---

## 2. Как выглядит одна запись

Каждое событие — одна строка. Разберём настоящую запись с этой машины:

```
Oct 12 14:36:21 ubuntu compiz: pam_failguard(unity:auth): pam_failguard: authentication refused for user [test], 1 failed logins, 7 s remaining
```

| Часть | Значение |
|---|---|
| `Oct 12 14:36:21` | когда произошло: 12 октября, 14:36:21 |
| `ubuntu` | на каком компьютере |
| `compiz` | какая программа записала событие |
| `pam_failguard(unity:auth)` | какая именно проверка пароля сработала |
| `...refused for user [test]...` | суть события словами |

**Два правила, о которых надо помнить:**

1. **Года в строке нет.** Он появляется только в старых копиях журнала. Если в
   отчёте важна дата — указывайте её полностью сами.
2. **Каждая попытка входа пишется отдельной строкой.** Сколько раз человек
   нажимал Enter — столько же строк.

## 3. Словарь записей

Главный раздел. Слева — как выглядит строка в журнале, справа — что это значит
человеческим языком.

Отметка **✓** означает: такая запись действительно встретилась при проверке
12.10.2026. Остальные — стандартные сообщения этой системы, они могут
появиться позже.

### 3.1. Вход по SSH

| Запись в журнале | Что это значит |
|---|---|
| ✓ `Accepted password for test from 10.0.2.2 port 49154 ssh2` | Пользователь `test` вошёл по SSH **с паролем** с адреса `10.0.2.2`. Вход успешный |
| `Accepted publickey for test from 10.0.2.2 ...` | Тот же вход, но **по ключу**, без пароля |
| ✓ `Failed password for test from 10.0.2.2 port 50044 ssh2` | Попытка входа **с неверным паролем**. Отказано |
| `Invalid user test from 10.0.2.2` | Попытка входа под **несуществующим** именем. Обычно перебор |
| ✓ `session opened for user test by (uid=0)` | Сессия SSH открыта, человек работает в системе |
| ✓ `session closed for user test` | Сессия SSH закрыта — вышел или соединение оборвалось |
| ✓ `Received disconnect from 10.0.2.2` | Соединение закрыто удалённой стороной |
| `Connection closed by ...` | Соединение закрыто, дословно «прервано клиентом» |

> **Адрес `10.0.2.2` — это сам компьютер.** В нашей схеме виртуальной машины так
> выглядит подключение с хост-машины. В обычной сети здесь был бы адрес
> реального соседнего компьютера.

### 3.2. Вход в графическую систему (окно с паролем)

| Запись в журнале | Что это значит |
|---|---|
| ✓ `pam_unix(lightdm:auth): authentication failure; ... user=test` | Неверный пароль в **окне входа** |
| ✓ `pam_unix(lightdm:session): session opened for user test by (uid=0)` | Успешный вход в графическую систему, сессия начата |
| ✓ `New session 42 of user test.` | Система зарегистрировала новую пользовательскую сессию |
| ✓ `Removed session 42.` | Сессия завершена |

### 3.3. Разблокировка заблокированного экрана

Самое важное для эксплуатации: в Ubuntu 15.10 разблокировку экрана проверяет
**программа `compiz`**, и в журнале она пишется под именем `unity`.

| Запись в журнале | Что это значит |
|---|---|
| ✓ `compiz: pam_unix(unity:auth): authentication failure; ... user=test` | На заблокированном экране введён **неверный пароль** |
| ✓ `compiz: pam_failguard(unity:auth): authentication refused for user [test], 1 failed logins, 7 s remaining` | Пароль **введён верный**, но вход отклонён: после неудачной попытки действует защита. Осталось 7 секунд |
| ✓ `compiz: gkr-pam: unlocked login keyring` | Экран разблокирован, хранилище паролей открыто |

> **Как это читать в отчёте.** Пара строк подряд означает: человек вошёл с
> неверным паролем, затем тут же ввёл верный — и был отклонён защитой. Одна
> строка `authentication failure` без следующей — просто опечатка.

### 3.4. Работа с правами администратора

| Запись в журнале | Что это значит |
|---|---|
| ✓ `sudo: test : TTY=pts/0 ; PWD=/home/test ; USER=root ; COMMAND=/bin/ls -la` | Пользователь `test` выполнил `/bin/ls -la` **от имени администратора** |
| ✓ `pam_unix(sudo:session): session opened for user root` | Права выданы, команда выполняется |
| ✓ `pam_unix(sudo:session): session closed for user root` | Выполнение завершено |
| `test is not in the sudoers file` | Пользователь попытался получить права, **ему отказано** |

> Здесь журнал пишет **введённую команду целиком**. Это самая ценная часть
> журнала для отчёта: видно, что именно человек делал.

### 3.5. Изменение учётных записей и паролей

| Запись в журнале | Что это значит |
|---|---|
| `new user: name=test, ...` | Создан новый пользователь `test` |
| `new group: name=..., ...` | Создана новая группа |
| `changed user test` | Изменены параметры пользователя `test` |
| `password changed for test` | У пользователя `test` сменён пароль |
| `pam_unix(chpasswd:auth): authentication failure` | Неверный пароль при смене пароля |

### 3.6. Служебные записи, которые не являются взломами

Их легко принять за инцидент. Это **обычная работа системы**:

| Запись в журнале | Что это на самом деле |
|---|---|
| ✓ `PAM unable to dlopen(pam_kwallet5.so): ... cannot open shared object file` | Модуль хранителя паролей не установлен. **Не инцидент** |
| ✓ `PAM adding faulty module: ...` | Продолжение предыдущей записи: PAM пропустил этот модуль и работает дальше |
| ✓ `polkitd: Registered Authentication Agent for ...` | Зарегистрирован графический диалог запроса пароля |
| ✓ `pkexec` | Запуск программы через систему разрешений — обычно с окном ввода пароля |
| ✓ `su: pam_unix(su:auth): authentication failure` | Неудачная попытка перехода в другой пользовательский account |

## 4. Как ответить на вопрос

Готовые команды. Ключ `-a` указан для надёжности — он ничего не ломает.

### Кто и когда последний раз заходил

```bash
grep -a "Accepted" /var/log/auth.log | tail -20
```

### Были ли неудачные попытки входа

```bash
grep -a "authentication failure\|Failed password" /var/log/auth.log
```

### Были ли попытки входа под несуществующими именами

```bash
grep -a "Invalid user" /var/log/auth.log
```

### Откуда приходили подключения по SSH

```bash
grep -a "sshd.*Accepted" /var/log/auth.log | grep -oaE "from [0-9a-f.:]+" | sort | uniq -c | sort -rn
```

> Ограничение `sshd.*Accepted` обязательно: без него в результат попадают
> записи `sudo`, где сама команда может содержать слово «Accepted».

### Что происходило с конкретным пользователем

```bash
grep -a "test" /var/log/auth.log
```

### Кто и когда получал права администратора

```bash
grep -a "sudo:" /var/log/auth.log
```

### Что происходило в конкретный день

```bash
grep -a "^Oct 12" /var/log/auth.log
```

### События только по SSH

```bash
grep -a "sshd" /var/log/auth.log
```

### Отказы защиты на блокировке экрана

```bash
grep -a "pam_failguard" /var/log/auth.log
```

## 5. Как выгрузить материал для отчёта

Чтобы в отчёте была проверяемая выдержка с датой и компьютером, копируйте строки
целиком — не пересказывайте. Отчёт читают другие люди, и они должны видеть
исходную запись.

**Выдержка одного события с контекстом:**

```bash
grep -a -B2 -A2 "Invalid user" /var/log/auth.log
```

**Всё по одному пользователю за конкретный день:**

```bash
grep -a "^Oct 12" /var/log/auth.log | grep -a "test"
```

**Выгрузка в отдельный файл для приложения к отчёту:**

```bash
grep -a "test" /var/log/auth.log > /tmp/vhod_test_12-10-2026.txt
```

> Обязательно указывайте в отчёте **дату, компьютер и имя пользователя** — в самом
> журнале года нет, а без этого выдержку нельзя будет проверить.

## 6. Границы журнала — что важно знать при работе с отчётами

1. **Хранится около месяца.** Ротация еженедельно, хранятся 4 копии. Данных
   старше ~4 недель уже не будет.

2. **Журнал можно стереть.** Копирования на другой сервер не настроено. Если файл
   удалён — история событий потеряна безвозвратно.

3. **Год в записях отсутствует.** См. раздел 2.

4. **Отдельного журнала действий пользователей нет.** Подробного аудита файлов и
   сетевых действий система не ведёт — фиксируются только входы и выдача прав.

5. **Журнал показывает и разрешённые действия.** В нём нет «злодея», есть
   факты. Выводы делает тот, кто читает.

6. **Свои команды видно в журнале, и это главная ловушка.** Всё, что
   администратор выполняет через `sudo`, записывается **целиком, вместе с
   текстом команды**. Если вы ищете, скажем, «попытки входа под несуществующим
   именем», то строка `sudo: ... COMMAND=grep -a Invalid user ...` попадёт в
   результат — и это будет не событие, а эхо вашего собственного запроса.

   Проверено на практике: поиск `Invalid user`, `password changed`, `new user`
   давал совпадения, хотя этих событий в системе не было.

   **Как отличить настоящее событие от эха:** настоящая запись начинается с
   имени программы-источника (`sshd`, `su`, `compiz`, `lightdm`, `passwd`),
   а эхо — со строки, где после `sudo:` идёт `test : TTY=...`.

   Простая проверка — отбросить такие строки:

   ```bash
   grep -av "sudo:     test" /var/log/auth.log
   ```

7. **Хранится копия в `journalctl`.** Те же события доступны командой
   `journalctl`, но она хранит данные только до перезагрузки. Для длительного
   хранения нужен именно `/var/log/auth.log`.

## 7. Справочные сведения

| Параметр | Значение |
|---|---|
| Путь | `/var/log/auth.log` |
| Владелец / группа | `syslog` / `adm` |
| Права | `0640` — читают только члены группы `adm` |
| Ротация | еженедельно, хранятся 4 копии, старые сжимаются |
| Копия в `journalctl` | да, до перезагрузки |

Кто реально пишет в журнал на проверяемой машине:

| Программа | Что записывает |
|---|---|
| `sshd` | подключения по SSH |
| `su` | переход в другой пользовательский account |
| `sudo` | выполнение команд с правами администратора |
| `compiz` | разблокировку экрана (сервис `unity`) |
| `lightdm` | вход в графическую систему |
| `systemd-logind` | открытие и закрытие сессий |
